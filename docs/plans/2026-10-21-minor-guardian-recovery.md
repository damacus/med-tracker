# Orphaned minor guardian recovery
Spec: owner answers on 21 October 2026 for #2707. Household owners and administrators may recover a minor who has no current effective guardian, including appointing a new guardian. This is the binding local specification.

## Global Constraints
- Implement in this isolated worktree on codex/feat-minor-guardian-recovery based on origin/main. Root Rust/Loco, Tera/DaisyUI, existing restricted-runtime/RLS harness. Read AGENTS, required Rust skills and ADRs0013–0016. Serena unavailable; use direct repository tools. Use Context7 for dependency-specific changes only.
- Explicit recovery is a narrow management exception. Preserve generic delegate_person denial and unsupported ordinary create/reactivate links. Never call delegation::assign/reactivate to recover; never create/reactivate accounts, household memberships or unrelated person grants. No adult/dependent-adult recovery, platform-role changes, live data, deployment or populated database resets.
- The subject must be a currently active minor participant in this household. Appointee must be a current active adult capable participant with a usable verified account in this same household. Reuse canonical eligibility semantics; reject a known adult age inconsistent with minor status. Both owner and administrator may restore or appoint. Ordinary members cannot.
- Orphan means no currently effective guardian in any household. A healthy link elsewhere blocks recovery without disclosing foreign identities. Evaluate authority with canonical live predicates including current account/membership, active relationship and nonterminal declaration. Check under locks; serialise competing recoveries across households by subject. Recheck actor, target eligibility, expected revision and orphan state on confirmation.
- Preserve immutable declaration provenance and terminal withdrawal. Extend the single guardian_declarations authority table with a source/basis and terminal supersession. New appointment is an administrator's declaration, not appointee consent or verified legal status. Store the actor truthfully; never rewrite old actor/guardian/subject fields. One open declaration per subject via partial unique index; old superseded authority can never revive. New appointee can withdraw through existing own declaration journey.
- Initial declarations remain one-time per subject lifetime: the initial-source insert policy/trigger must reject any previous declaration history, including terminal rows. Removing the old global UNIQUE constraint must not permit ordinary members to self-declare again. Administrative-source inserts require the dedicated checked recovery path. Source/basis is immutable.
- A restore activates only the exact inactive relationship linked to an eligible open declaration; withdrawn/superseded declarations cannot restore. Appointment may follow withdrawal or replace an unusable open declaration; close the old open row by terminal supersession and insert a new source-specific row atomically. Existing terminal rows stay unchanged.
- Confirmation uses an opaque, database-generated random UUID and revision from the latest declaration history by declaration time, including terminal rows. The UUID rotates on terminal transition; a fixed no-history marker applies only before any declaration exists. A second opaque UUID tracks the current local open declaration's exact relationship and rotates on activation/deactivation, so restore/deactivate ABA invalidates old forms. Fixed nil marks absence of that local link. These snapshots detect stale confirmation and never grant authority. Foreign identities are not exposed.
- Birthday checks for recovery use the database clock across UTC−12 through UTC+14. A foreign guardian who could be an adult in any supported zone blocks takeover; a subject or appointee must be unambiguously eligible across that span. Recovery may be unavailable around an eighteenth birthday for up to the worldwide offset span of about 26 hours. The browser must explain this temporary restriction.
- A temporary login lockout on an existing guardian does not make that guardian's active declaration and relationship orphaned. The actor and proposed appointee must still have usable, unlocked accounts. Ordinary initial declaration eligibility keeps its pre-recovery birthday semantics.
- Forced RLS applies to table owners too. Any global-check definer requires explicit, narrow owner read policies on its underlying forced-RLS tables; merely changing function owner is insufficient. Fixed-path helper access must expose only the approved boolean/command and must not create an app SELECT bypass.
- Use a fresh additive migration, not changes to previously applied migrations. Keep forced RLS and restricted app grants. If hidden foreign authority requires a narrow SECURITY DEFINER boolean/command, constrain current actor/household/subject, fixed search_path/owner/execute privileges and prove negative SQL tests. Never disable RLS or run app operations as owner.
- Typed domain commands/IDs/results, no internal JSON roundtrip. Keep SQL filtering/bounded lists and safe structured errors. Transactions include permission version effects and attributable audit. Recovery requires deliberate confirmation and a short reason stored in attributable audit without clinical detail.
- API additions must be additive, mirrored in OpenAPI/Android generated client through repository tooling. Preserve existing own IDs/paging/withdrawal contracts; expose source/superseded state truthfully in own history and hide terminal withdraw controls. No new public recovery API is required: browser can call dedicated domain command.
- Fish/RTK/Task wrappers; meaningful failing behavioural tests before executable changes. No broad lint suppressions, unrelated comments/refactors or Rails edits. One implementation writer at a time, no nested agents or worker publication. Check author/committer/signing before every commit; controller runs final frozen task ci/docs build and independent reviews. No merge/deploy.
