## Smallest dependency sequence

1. **Issued credential and household selection.** The existing Rust HTTP contract is `rust/contract-tests/tests/oauth.rs`: discovery, public client, `/authorize` redirect to `/login`, CSRF-protected password form, consent, PKCE `/token` exchange, refresh rotation and revocation. Its issued bearer must read `GET /api/v1/auth/households` (case `issued_code_enforces_pkce_and_supports_refresh_rotation_and_revocation`). `rust/contract-tests/tests/auth.rs` covers the household payload, revoked/expired/locked credentials, operational membership and session invalidation. The Rails routes are `config/routes.rb:24-31`; Rails authority is `app/controllers/api/v1/auth/sessions_controller.rb:20-30,121-140` and Rodauth in `app/misc/rodauth_main.rb`. The current Rust bearer verifier in `rust/api/src/lib.rs:177-397` only consumes already-issued ApiSession/mobile OAuth credentials for a requested household; it cannot issue one or list households. Preserve Rodauth's active-account/lockout, CSRF, consent, S256 PKCE, session inactivity/maximum age, MFA and passkey checks. In particular, `app/misc/rodauth_main.rb:342-365,397-462` shows login and MFA state; a successful password check alone cannot be treated as complete authorization.

2. **Medication and direct dose.** The already-implemented Rust `GET /api/v1/households/:household_id/medications` and `/:id` can supply the selected medication and stock; `rust/contract-tests/tests/medication_read_api.rs` and `medication_mobile_oauth_api.rs` cover scope, current membership, hidden records and OAuth activity. For the shortest dose loop, use the existing public `GET/POST /api/v1/households/:household_id/medication_takes` contract (`config/routes.rb:84`, `rust/contract-tests/tests/doses.rs:940-1151`). The `medication_takes_create_filters_paginates_and_preserves_precision` case proves authorized create, client UUID replay, 1.25 stock decrement, ETag, audit and history collection; the neighbouring cases cover grants, invalid input, future time and no stock loss. Rails implementation is `app/controllers/api/v1/medication_takes_controller.rb:17-86`, with the domain write delegated to `MedicationAdministration::RecordDose`. Fixture and HTTP helpers already exist in `rust/contract-tests/src/lib.rs`; `rust/contract-tests/tests/doses.rs:208-274` creates a medication and routine assignment without adding inventory tooling.

3. **Scheduled dose once the direct loop works.** `config/routes.rb:58-82` publishes schedule and direct-assignment `GET .../dose_occurrences` plus `POST .../take`, `POST .../not_taken`, and `PATCH .../reopen`. `rust/contract-tests/tests/doses.rs:276-939` covers occurrence projection, immutable/idempotent outcomes, ETags and stock effects for schedule and assignment sources. Rails action/authorization is `app/controllers/api/v1/dose_occurrences_controller.rb:10-90`. This is a separate write boundary from the direct medication-take route and should retain its version and cycle-key preconditions. Both sources feed the medication-take history route above.

4. **Leptos connection.** `rust/web/src/lib.rs` supplies server-rendered `/login` HTML only; `rust/web/tests/login.smoke.test.mjs` checks desktop/mobile rendering and explicitly sees a disabled submit button. Connect the form to the verified authentication flow, then household selection, medication read, direct-dose action and refreshed stock/history. Keep the UI milestone dependent on actual HTTP issuance and write routes; a static screen cannot prove the journey.
