# Leptos UI component options

**Reviewed:** 30 September 2026

This is a read-only recommendation for the dashboard preview. Rails remains the reference for text, tokens, mobile navigation and disclosure styling. Keep the preview dashboard-only, server-rendered and read-only. This comparison does not select or install a library.

## Current boundary

`rust/web/Cargo.toml` declares Leptos `0.8.14` and Axum `0.8.4` as caret requirements. `rust/web/Cargo.lock` currently resolves Leptos `0.8.21` and Axum `0.8.9`; these are locked versions, not exact manifest pins. The dashboard emits HTML with `view!`, serves `/dashboard.css` and a small `/dashboard.js`, and has no hydration feature or browser WASM entry point. Native HTML, links, forms and the existing JavaScript can work with SSR alone. Leptos event handlers require its separate WASM hydration build ([Leptos 0.8 SSR notes](https://github.com/leptos-rs/leptos/blob/v0.8.14/examples/SSR_NOTES.md)).

Rails already defines Tailwind 4 tokens, fonts and RubyUI/Phlex markup in `app/assets/tailwind/application.css` and the Rails UI components. Those Ruby components cannot run in Rust. Leptos could emit equivalent HTML and classes, but the asset and controller integration described below is untested.

## Options

| Approach | What it provides | Controls and accessibility | Build and runtime cost |
|---|---|---|---|
| Reuse selected Rails markup, tokens and Stimulus controllers | Best chance of preserving the current Rails appearance. Tailwind can scan Rust sources using [`@source`](https://tailwindcss.com/docs/detecting-classes-in-source-files). Stimulus binds controllers through HTML attributes ([controllers](https://stimulus.hotwired.dev/reference/controllers), [targets and actions](https://stimulus.hotwired.dev/reference/targets)). | The Rails dropdown is a candidate: its controller uses Stimulus and Floating UI. Audit each controller and its emitted markup before reusing it. RubyUI supplies markup/classes, not runnable Rust components. The Leptos-to-Stimulus adapter is **untested**; keyboard, focus, ARIA and mobile behaviour must be verified in the consuming app. | Compile CSS against reused classes; bundle and serve selected JS modules and dependencies; register controller identifiers and manage asset versions in Axum. Rails importmap pins and asset paths do not transfer automatically. No Leptos hydration is needed for standalone Stimulus behaviour. |
| Tailwind 4 + daisyUI 5 | CSS/HTML component styles with themes and selective component configuration. Official install uses the CSS `@plugin` directive ([CLI setup](https://daisyui.com/docs/install/cli/)); licence is MIT ([intro](https://daisyui.com/docs/intro/)). The docs showed 5.7.x, with patch versions varying between pages. | Includes `<details>`/popover dropdown, checkbox drawer, dock for bottom navigation, select styling and accordion ([dropdown](https://daisyui.com/components/dropdown/), [drawer](https://daisyui.com/components/drawer/), [dock](https://daisyui.com/components/dock/), [select](https://daisyui.com/components/select/), [accordion](https://daisyui.com/components/accordion/)). Styling and HTML patterns do not guarantee focus trapping, menu keyboard semantics or correct ARIA state. The app must use links for navigation and verify accessibility. | Add a pinned Node/CSS build and serve compiled CSS. Native patterns remain SSR; no Leptos hydration is needed for their basic browser behaviour. Map Rails tokens and tune component appearance. Keep existing SVGs; no icon set is included. |
| Tailwind 4 + Flowbite 4 | Tailwind styles plus JavaScript behaviour on data attributes. The official quickstart documents Tailwind 4, plugin/source setup and a browser JS bundle ([quickstart](https://flowbite.com/docs/getting-started/quickstart/)); Flowbite is MIT ([introduction](https://flowbite.com/docs/getting-started/introduction/)). The CDN example names 4.0.1. | Provides JS dropdown, drawer, modal, bottom navigation, select styling and accordion ([dropdown](https://flowbite.com/docs/components/dropdowns/), [drawer](https://flowbite.com/docs/components/drawer/), [bottom navigation](https://flowbite.com/docs/components/bottom-navigation/), [select](https://flowbite.com/docs/forms/select/), [accordion](https://flowbite.com/docs/components/accordion/)). Data attributes can operate on SSR HTML without Leptos hydration. Docs describe required attributes, but the app still must test focus containment/return, Escape, keyboard behaviour and accessible names. | Build Tailwind CSS and bundle Flowbite browser JS. Initialise the controls on SSR HTML; call `initFlowbite()` again after framework DOM updates if those are introduced ([JavaScript integration](https://flowbite.com/docs/getting-started/javascript/)). Token mapping and appearance tuning are required. Bundle impact here is unmeasured. |
| Thaw | Native Leptos component library with Fluent styling. Its compatibility table maps `0.5.0-beta` to Leptos 0.8; the workspace dependency declares Leptos 0.8.5 and the crate manifest has `ssr`/`hydrate` features ([project](https://github.com/thaw-ui/thaw), [workspace manifest](https://github.com/thaw-ui/thaw/blob/main/Cargo.toml), [crate manifest](https://github.com/thaw-ui/thaw/blob/main/thaw/Cargo.toml)). MIT licence. | Exact dashboard coverage and accessible behaviour for dropdown, drawer, bottom navigation, select and accordion were **not individually verified**. Do not infer coverage from the library size. | Requires Rust component integration; interactive Rust handlers need hydration/WASM and its asset pipeline. Fluent appearance differs from Rails tokens. Compatibility with locked Leptos 0.8.21 and SSR/hydration is **unverified**; beta status increases adoption risk. |
| Radix-Leptos | Headless Leptos primitives with no prescribed visual system. README documents version `0.9.0` and Leptos 0.8.8; licence is MIT ([README](https://github.com/cloud-shuttle/radix-leptos), [licence](https://github.com/cloud-shuttle/radix-leptos/blob/main/LICENSE)). | README claims accessible primitives including button, dialog and select. Dropdown/drawer/accordion coverage and actual keyboard behaviour need component-level proof. There is no styled bottom navigation or icon set. Headless claims are not a substitute for testing the consuming app. | App authors supply styling and layout. Interactive primitives need hydration/WASM; SSR alone gives initial markup without client event behaviour. Compatibility with locked Leptos 0.8.21 is **unverified**. |

The Leptos shadcn port is another styled candidate, but its README gives conflicting component/package/status versions (`0.4.0`, `0.5.0` and `0.2.0`) and no verified compile or SSR/hydration result against locked Leptos 0.8.21 ([project](https://github.com/cloud-shuttle/leptos-shadcn-ui)). Keep it out of the adoption path pending clarification. The original [shadcn/ui](https://github.com/shadcn-ui/ui) is React-based and cannot be used directly as Leptos components.

## Recommendation

Keep the current native HTML controls and SSR-first runtime. First, prototype a narrow Rails asset adapter on one dashboard card and dropdown: have Leptos emit equivalent RubyUI classes and data attributes, reuse Rails tokens, and bundle only the needed Stimulus controller. This is an inference from the inspected source, not a proven integration. Compare it with Rails at desktop and mobile sizes, and test keyboard, focus, ARIA and disclosure behaviour. If the adapter costs more than it saves, prototype pinned Tailwind 4 + daisyUI 5 CSS instead. Scan Rust class literals explicitly, map Rails tokens, and keep SVGs local.

Add hydration only if native HTML plus a small JavaScript controller cannot meet the requirements for a specific control. Then build one interactive control as a compile, SSR/hydration, accessibility and bundle-size spike before considering Thaw or Radix-Leptos. Pin exact versions during any future evaluation. Do not migrate the whole dashboard to a new design system in one step.

Whichever style/behaviour system is chosen, put a thin shared Leptos component layer above it. Page authors should compose reusable buttons, disclosures, navigation items and form controls rather than duplicate utility strings or invent local CSS on every page. This layer can standardise Rails-derived tokens and accessible markup without requiring a full component library.

## Checks before adoption

- A CSS pack supplies appearance and HTML patterns; Flowbite also supplies browser JavaScript. A Leptos library supplies Rust APIs, while headless primitives generally leave styling to the app. None automatically preserves Rails parity.
- Compare any drawer with the current native `<dialog>` for Escape, focus return and modal focus containment. Verify dropdown menu semantics and keyboard operation; do not treat visual open/closed state as accessible behaviour.
- Use actual links for available bottom navigation and preserve the read-only preview's disabled/unavailable actions. Check iOS safe-area spacing; daisyUI's dock docs call out `viewport-fit=cover` ([dock](https://daisyui.com/components/dock/)).
- Extract shared tokens if importing Rails CSS would bring Rails-only selectors, fonts or asset paths. Verify contrast and mobile spacing.
- No candidate library was compiled or accessibility-tested against this checkout. Recheck current manifests, maintenance, security and licence at adoption time.
