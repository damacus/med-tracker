# Shared reads and browser session: test brief

Preparation only. The direct-dose runtime manifest remains frozen. Add these tests in the next web tranche, beginning with an HTTP RED against the existing Axum API. Keep the browser and native clients on the same `/api/v1` routes described in `journey-web-boundary.md`; do not add a web-only source lookup.

## Shared read contracts

Use the disposable owner, restricted viewer, managed person, hidden person, schedule, and person-medication records already provisioned for contract tests. Exercise public HTTP, not handler functions or database queries for the response.

1. Parameterize GET collections for `/households/{id}/people`, `/schedules`, and `/person_medications`. Each returns `data` and `meta`, includes its visible managed record, and excludes records for an ungranted person and a foreign household. The schedule and assignment rows must carry their person and medication IDs and portable IDs, decimal dose string and unit, active/paused state, and `can_manage`. The person row must expose the identity and profile fields needed by the picker. For a view-only grant, the rows remain readable while `can_manage` is false; this does not imply permission to record a dose.
2. On each collection, request `page=1&per_page=1` and `page=2&per_page=1`: rows follow ascending ID order without overlap, with correct `page`, `per_page`, and `total_count`. A later `updated_since` returns no older fixture rows; invalid ISO8601 returns the Rails-style 422 error. Check the existing 1..100 page-size clamp in one representative collection. The Rails collection helper orders by ID and applies the filter before pagination.
3. GET a visible person, schedule, and assignment by ID and verify the same representation as the corresponding collection row plus `ETag`. Schedule and assignment detail should also accept their existing portable IDs. Hidden or foreign resource detail must not reveal a record; a foreign household path is denied. Recheck a revoked person grant so the same viewer no longer sees the person or linked sources on the next request. Do not infer record permission from a previously rendered picker.

Rails authorities: `Api::V1::{People,Schedules,PersonMedications}Controller` index/show, their serializers and policies, and OpenAPI `listPeople`, `listSchedules`, `listPersonMedications` plus detail schemas. Current Rails scopes return **visible current** sources; the web picker may display active/paused eligibility from response fields, but the API tests must not silently exclude a visible inactive source from the read contract.

## Browser credential and shared API cases

1. GET `/login` starts a short-lived signed login intent and renders a labelled, CSRF-protected form. A wrong password or missing/wrong login CSRF token creates no browser session. A correct password for the fixture owner creates a signed browser cookie, leads to an authorised household choice or the supported empty state, then allows the three shared collections and medication/take reads through cookie authentication. Assert that HTML, URLs, JavaScript and browser storage contain no API bearer or refresh token. A client-supplied return URL cannot redirect off origin. Keep the existing OAuth login/consent test selection green.
2. The same shared API read and direct-dose POST work with a native bearer and with the browser cookie for the same active owner, producing the same data and permission outcome. A valid cookie plus an explicitly supplied invalid `Authorization: Bearer ...` returns 401 on both a read and dose POST, even if the cookie and CSRF token are valid; it must not fall back to the cookie or write a take. This precedence is an explicit security boundary.
3. For cookie-authenticated dose POST, missing or wrong session CSRF, an untrusted `Origin`/`Referer`, and a spoofed incoming `Host` cannot produce a take, stock change or domain audit version. A valid session CSRF and configured public origin succeed. Native bearer POST retains the existing contract without browser CSRF. Repeat the cookie POST with its original client UUID, including after a validation rerender, and assert one take and one stock decrement; a changed payload with that UUID conflicts.
4. After a successful cookie read, remove its `account_active_session_keys` row, move `last_use` past configured inactivity, or move `created_at` past a configured absolute deadline in separate disposable cases. A copied old cookie then fails on both web and shared API routes. Revoke membership, revoke the managed-person grant, deactivate the user/account, or make the household non-operational in focused fixture variants; each next request must re-evaluate the relevant permission and deny affected data/writes. Preserve the distinction between 401 for invalid session and 403 for a valid session lacking household/person authority.
5. POST `/logout` with session CSRF clears the cookie and invalidates its backing browser session; a copied pre-logout cookie no longer reads the API or web page. Missing/wrong CSRF and a cross-origin logout do not invalidate the current session. Test whether an independently issued mobile OAuth grant remains valid according to the confirmed Rails logout behavior before fixing that expectation in the contract. Do not treat OpenAPI `DELETE /auth/logout` (bearer credential revocation) as browser logout.

## Test shape and stop line

Add a small HTTP contract file for shared reads and cookie API boundaries; use one browser flow for actual sign-in, household choice, form submission, visible error/focus, stock and history on desktop and mobile. Reuse isolated Compose, its disposable fixture and browser sidecar. Database changes used to simulate expiry or revocation are setup only; assertions remain on public HTTP and observable stock/audit effects. Coordinate any new fixture fields with the fixture owner before the next runtime freeze, establish RED first, then let the runner own combined green acceptance.

This brief excludes people/source CRUD, scheduled-occurrence actions, MFA completion, account recovery, remember-me parity, and broader offline/PWA behavior.
