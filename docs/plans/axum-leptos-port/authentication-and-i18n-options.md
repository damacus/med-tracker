# Authentication and i18n options

**Reviewed:** 30 September 2026

This is research for the read-only Rust dashboard. Rails and Rodauth remain the product and security reference. The dashboard stays server-rendered, read-only and without hydration in this work. No identity platform, authentication implementation, locale conversion or dependency is selected here.

## Existing authentication contract

MedTracker enables Rodauth account creation and verification, login/logout, remember-me, lockout and active sessions, password reset/change, login change and verification, account closure, OIDC client login, OTP and recovery codes, WebAuthn login/autofill, and OAuth PKCE and revocation (`app/misc/rodauth_main.rb:10-28`). Rodauth uses Sequel over the Active Record connection, the `accounts.password_hash` field, and Rails rendering and mailers (`:31-100`). Verification, reset, login-change and unlock messages are queued after commit. Password policy is 12 characters minimum and 72 bytes maximum with a number and special character; lockout follows five failures for 30 minutes (`:104-112,363-379`). Session and token ages are configurable; OAuth access lasts 15 minutes and refresh tokens rotate (`:18-28,339-402`).

Application hooks also enforce deactivated-account checks, invite-only registration and adult date-of-birth requirements; atomically create account, person, user, household and invitation records; preserve medication history at closure; require WebAuthn verification; set an MFA step-up timestamp; and audit credential and OAuth consent/revocation events (`app/misc/rodauth_main.rb:140-265,308-335,390-565,609-665`). Zitadel is currently an OIDC client path; its `amr` claim only waives local MFA after an MFA-authenticated IdP login (`:319-335,467-485,691-712`). Native clients also depend on MedTracker's OAuth provider: S256 PKCE, account-bound grants, short access tokens, rotating refresh tokens and revocation (`app/misc/rodauth_mobile_oauth.rb`; `spec/requests/mobile_oauth_authorization_spec.rb`). Authentication is coupled to household membership, roles and audit history.

Rust already implements local login/logout, OAuth discovery, authorization, token and revoke endpoints, and API session list/revoke/logout (`rust/api/src/oauth.rs`, `rust/api/src/auth_sessions.rs`). It checks existing bcrypt hashes, active account/user state and lockout, issues signed browser cookies backed by `account_active_session_keys`, enforces session ages, and denies password-only login when OTP, passkey or recovery credentials are enrolled. Contract tests cover PKCE, consent, refresh rotation/revocation, CSRF, enrolled-factor denial, expiry/lockout and session revocation; these test cases were inspected, not run for this research. Rust does not yet implement registration/verification, reset (currently 501), password or email changes, remember-me, MFA challenge, WebAuthn enrolment/authentication, recovery codes, OIDC client login, or the complete account lifecycle hooks. This is partial parity, not a Rodauth replacement. The Rust UI also currently sets `lang="en"` (`rust/web/src/lib.rs:125-134`).

## Identity choices and migration gates

| Option | Evidence and boundary |
|---|---|
| Keep Rodauth behind a stable identity boundary | Preserves the existing lifecycle, MFA, passkeys and grant semantics for this dashboard slice. Define issuer/subject, household and role claims, session invalidation, logout and revocation before Rust consumes identity. A Rodauth-backed OIDC boundary would itself need implementation and proof. |
| `axum-login` with `tower-sessions` | [axum-login](https://github.com/maxcountryman/axum-login) supplies user/backend traits, login/logout and permission checks; [tower-sessions](https://github.com/maxcountryman/tower-sessions) supplies session stores including PostgreSQL. These are primitives, not an identity provider: account lifecycle, MFA/WebAuthn, mail, OAuth provider policy and MedTracker audits remain application work. Rust already has a bespoke session path. |
| Existing Zitadel service | [Hosted login](https://zitadel.com/docs/guides/integrate/login/hosted-login) includes reset, MFA and passkeys; [Actions v2](https://zitadel.com/docs/concepts/features/actions_v2) exposes hooks; its [user migration guide](https://zitadel.com/docs/guides/migrate/users) documents bcrypt import. This is a candidate external identity service, but mapping atomic household creation, invitations, session revocation and native grants needs explicit contracts. Its hooks are not equivalent to Rodauth's in-process Ruby hooks. |
| Keycloak | Its [server developer guide](https://www.keycloak.org/docs/latest/server_development/index.html) documents authenticator, required-action and event-listener SPIs. It adds Java provider packaging and another operated service; those SPIs do not implement MedTracker policy automatically. |
| Kanidm | [Kanidm](https://kanidm.github.io/) is a Rust identity service with [credentials and passkeys](https://kanidm.github.io/kanidm/master/accounts/authentication_and_credentials.html) and [OAuth2/OIDC](https://kanidm.github.io/kanidm/master/integrations/oauth2.html). It is a credible Rust-owned service candidate, with separate operations, data and policy mapping. OIDC support alone does not establish MedTracker account hooks, native scopes or grants. |

Do not treat a Rust OIDC client as a replacement for Rodauth's account lifecycle or MedTracker's OAuth authorization server. MedTracker's OAuth discovery endpoint is not automatically OIDC discovery. Any identity change must prove bcrypt verification and rehash behaviour; MFA enrolment, challenge and recovery; reset/verification token expiry and one-time use; remember/session revocation; post-commit mail; deactivated users; audit events; closure history preservation; household/role changes; and native S256 PKCE, consent, refresh rotation, revocation, client registration and scopes. Preserve stable account IDs and enforce household isolation. Keep the current password-only Rust path behind this identity decision for protected product features.

## Translation sources and conversion

Rails locale sources are `config/locales/{en,cy,ga,es,pt}.yml`; Rails I18n fallback is enabled in `config/application.rb:58`. Files have a top-level locale wrapper, nested keys, `%{name}` interpolation, nested `one`/`other` plural maps, and framework `activerecord`/`rodauth` namespaces as well as dashboard text (`config/locales/en.yml:1-70,2320-2390`). Dashboard date/time output also includes raw `strftime` calls (`app/components/dashboard/index_view.rb:47,330`), so translating strings alone would not localise dates.

The Rust web lockfile resolves Leptos **0.8.21**; its manifest allows `0.8.14+` (`rust/web/Cargo.toml:10`). [`leptos_i18n`](https://github.com/Baptistemontan/leptos_i18n) documents version **0.6.x** for the Leptos 0.8 line and setup as `"0.6"`; [docs.rs](https://docs.rs/leptos_i18n/latest/leptos_i18n/) labels 0.6.2 latest. This is compatibility-line evidence only. The crate has not been compiled against the locked 0.8.21 in this repository. Its build script generates compile-time checked keys and interpolation; JSON is the default, with YAML, JSON5 and TOML documented ([configuration](https://baptistemontan.github.io/leptos_i18n/setting_up/01_configuration.html), [file structure](https://baptistemontan.github.io/leptos_i18n/setting_up/02_file_structure.html)).

Conversion is not a direct file copy: Leptos expects locale files without Rails' wrapper, `{{ name }}` placeholders instead of `%{name}`, and plural siblings such as `task_count_one` and `task_count_other` ([interpolation](https://baptistemontan.github.io/leptos_i18n/declare/02_interpolation.html), [plural declarations](https://baptistemontan.github.io/leptos_i18n/declare/03_plurals.html)). An exporter should select only UI keys used by the Rust dashboard, convert placeholders and plural maps deliberately, flag non-string or HTML-sensitive values, and compare keys and placeholders across all five locales. Keep Rails YAML authoritative while both applications coexist. Test plural output for 0, 1 and 2 and Welsh/Irish edge cases. The cited project documents ICU4X number/date/plural formatting, namespace files, explicit locale inheritance/fallback and locale direction ([formatting](https://github.com/Baptistemontan/leptos_i18n/blob/master/docs/book/src/usage/09_t_format.md), [namespaces](https://baptistemontan.github.io/leptos_i18n/setting_up/03_namespaces.html), [inheritance](https://baptistemontan.github.io/leptos_i18n/setting_up/04_inheritance.html), [features](https://baptistemontan.github.io/leptos_i18n/06_features.html)).

Documented locale resolution checks URL prefix when routing uses it, cookie, SSR `Accept-Language`, browser languages for CSR, then default; SSR selects the initial locale and the client does not recalculate it on load ([locale resolution](https://baptistemontan.github.io/leptos_i18n/infos/01_locale_resol.html)). The actual Axum/Leptos render path has not been proven with this crate. Any prototype should assert translated initial HTML, `<html lang>` and `dir` for `Accept-Language` and cookie requests, plus fallback and missing-key behaviour. If hydration is later considered, test server/client feature combinations and verify no text mismatch or language flash. The current five locales are LTR; wire `dir` from locale for future RTL support.

## Bounded proof of concept

1. In an isolated branch, compile `leptos_i18n` 0.6.x with locked Leptos 0.8.21 for the server and a hydration target only if hydration is planned; record the resolved patch and feature set.
2. Convert a small greeting, task count, stock summary and due-time sample from the five Rails files. Fail on missing/mismatched keys, placeholders, plural categories, unsupported YAML values and duplicate keys; compare Rails output for 0, 1, 2 and Welsh/Irish cases.
3. Request each locale by cookie and `Accept-Language`; assert translated initial HTML, `lang`, `dir`, fallback and one missing key. If hydration is added, assert no language flash or server/client text mismatch.
4. Separately select an identity boundary and black-box test active, locked and deactivated users, MFA, session revocation, native PKCE and refresh rotation before changing protected-feature login.

All crate compatibility and integration behaviour above is uncompiled and unverified in MedTracker. No source, dependency or authentication changes were made for this research.
