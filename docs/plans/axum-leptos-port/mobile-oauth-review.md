# Mobile OAuth medication read review

## Rails requirements baseline

- Access-token lookup uses `Base64.urlsafe_encode64(Digest::SHA256.digest(token.to_s))` with Ruby's default padding, then selects an unrevoked `oauth_grants` row whose `expires_in` is at or after the current time. This differs from the hexadecimal digest for `api_sessions`. See `app/models/oauth_grant.rb:17-26` and `app/models/api_session.rb:33-43`.
- A mobile grant is account based: `client_kind = mobile`, `household_membership_id`, `person_id`, and `permissions_version` are null, and `authenticated_at` and `last_used_at` exist. The database check constraint enforces this shape. The grant must include the exact `medtracker` scope, separated by whitespace. See `db/schema.rb:994-1028` and `app/models/oauth_grant.rb:38-40`.
- An active login requires `last_used_at > now - SESSION_INACTIVITY_TIMEOUT_DAYS` (default 30 days). When `SESSION_MAX_AGE_DAYS` is positive, it also requires `authenticated_at > now - maximum age`; the default zero disables the maximum age. The boundary is strict. See `app/models/oauth_grant.rb:43-49` and `app/services/authentication_lifetime.rb:3-10`.
- The account must be verified, have a linked person with an active user, and have no active `AccountLockout`. These checks occur before the request gains tenant context. Rails updates `last_used_at` after binding the account context, before checking the requested household; even a subsequently forbidden household request can refresh activity. See `app/models/oauth_grant.rb:81-83`, `app/controllers/api/v1/base_controller.rb:60-80,103-105`, and `app/services/api_auth_state.rb:16-20`.
- An account grant does not choose a household at issue time. For the requested household, reselect a current active membership belonging to the grant account and require the household to be operational. Revoked membership denies that household without revoking access to another current household. See `app/controllers/api/v1/base_controller.rb:83-100` and `spec/requests/mobile_oauth_authorization_spec.rb:343-371`.
- For medication reads, managers (owner or administrator) see all household medications. Members see medicines linked through a schedule or person-medication assignment to a person for whom their current membership has an active `view` or stronger `PersonAccessGrant`; they also see medicines they created while still unlinked to any schedule or person-medication assignment. List and show use the same policy scope. See `app/policies/medication_policy.rb:50-82` and `app/policies/concerns/policy_helpers.rb:24-37,63-97`.
- Rails enters a transaction, sets account context first, then household and membership context. Forced RLS allows account lookup of the account's memberships, then restricts medication and other tenant rows to the current household. The Rust path must retain the restricted `med_tracker_app` role and transaction-local context. See `app/services/tenant_context.rb:11-19,74-85`, `db/schema.rb:1650-1692`, and `rust/api/src/lib.rs:31-55`.
- Successful and authorised read audit context identifies `authentication_method: oauth` and `session_reference: oauth_grant:<id>` with current account, user, membership, role, permissions version, and household. The bearer and digest do not belong in audit metadata. ApiSession remains `api_session:<id>`. See `app/services/audit/context.rb:62-89`, `app/controllers/api/v1/base_controller.rb:123-152`, and `rust/api/src/audit.rs:17-46`.

## Review status

Requirements baseline sent to the orchestrator and both writers on 25 September 2026. Source review finds the padded digest, strict login deadlines, account and lockout checks, current membership lookup, OAuth audit identity, and activity-preserving household-denial commit aligned with Rails. The bounded invalid-filter 422 path also commits authenticated OAuth activity. The existing ApiSession branch remains structurally intact and passed the combined medication read HTTP cases. Invalid lifetime environment values fail closed with a 401 in Rust; Rails raises on invalid configuration, so this is an intentional safer operational difference rather than exact error parity. A database or audit failure still rolls back the touch with its transaction, which avoids persisting a partial result; full activity parity is not claimed.

Two acceptance-test gaps were returned to the test writer and addressed in the frozen source: `old_login` has a fresh `last_used_at` while the disposable Rust service sets `SESSION_MAX_AGE_DAYS=30`; separate `view` and `revoked_view` grants test linked medication visibility. The original `stale_login` case still covers inactivity. The suite also checks 403 and 422 activity refresh. All seven OAuth HTTP cases passed in each final overlapping run.

## Combined tranche verdicts

**Requirements: clean for the bounded mobile OAuth medication read slice.** The final product source uses Rails' padded URL-safe token hash, unrevoked/unexpired grant, exact `medtracker` scope, strict inactivity and optional maximum login age, verified/unlocked active account, and current membership in an operational requested household. Medication scope retains current manager, person-grant, and member-created-unlinked rules under the restricted PostgreSQL role. OAuth audits use `oauth_grant:<id>` without bearer material. The independent test writer proved a valid-grant red (401 instead of 200 before product changes); two overlapping disposable runs later passed forecast 3/3, OAuth 7/7, and read 9/9 each. No issuance, refresh, writes, or broader API parity is claimed.

**Code quality and security: clean for the reviewed source, with the evidence limits below.** The API retains transaction-local account/household/membership settings and the existing ApiSession branch. Known 403/404 household denial and invalid-filter 422 paths commit a validated OAuth activity touch; database/audit failures roll it back. The runner uses a test sidecar sharing the API service network namespace, so loopback passes the existing target guard without publishing the Rust API port. Project-specific image, fixture bind and cleanup are guarded. The optional subnet override is macOS-only, checks Docker IPv4 subnet intersections, and compares the candidate network address's route with the default route. That single-address check is not proof against every more-specific host route inside the /28; the chosen pair was separately checked against the host route inventory. No actionable source finding remains after the corrected runner and test cases.

**Evidence limits.** The 19/19 result for each project is real HTTP evidence, and the projects had distinct IDs, fixtures, API container IDs and configured /28 networks. The 43-file before/after input digest matched, but its manifest omitted the new subnet override and validator, so it is not a complete byte-for-byte stability proof. The event/log evidence supports overlapping runs but lacks a single point-in-time `docker ps` snapshot with both API IDs. No-host-port is established by Compose configuration. The migrated-database audit ledger append, representative load/memory, and complete API parity remain open. This review lane ran no tests itself; runner and writer reports own command evidence.

The team charter and retrospective accurately distinguish the current parallel-writer exception from the historical single-writer plan, and they avoid claiming measured time or cost savings. The opening execution update in `plan.md` makes the supersession explicit. The retro's earlier 12 focused HTTP and three unit checks describe the baseline medication slice, not the new OAuth acceptance count.

The earlier smoke found two tooling defects: `CONTRACT_FIXTURE_DIR` now separates the absolute fixture bind from the relative cleanup path, and a sidecar uses `http://127.0.0.1:39998` under the existing target guard. The final overlapping runs passed and the runner reported removal of containers, networks, images, volumes and storage. The separate `task contract:isolation` gate passed with two explicit subnets: each project saw its own fixture and no peer account under PostgreSQL 18.6; first-project cleanup preserved the peer; a deliberately failed Rust target cleaned up; final cleanup left no contract networks or owner markers. The default-network attempt had been blocked by Docker address-pool exhaustion, so the explicit-subnet pass is the applicable isolation result for this host.
