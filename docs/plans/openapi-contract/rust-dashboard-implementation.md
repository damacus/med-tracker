The Rust dashboard does not reuse the dose-writing steps in `spec/system/dashboard_spec.rb`, Rails action links, report navigation, or the `time_first`, `family_lanes` and `calm_focus` experiments in `spec/requests/dashboard_home_spec.rb`. It does not port the Smart Insights engine examples that claim analysis or a detected pattern. The reference screenshot supplies appearance only; its real names, avatar and medicines are excluded from fixtures and published screenshots.

The reference uses Rails' `theme-serene-sage` palette (`#7DAA92`) and Inter font in `app/assets/tailwind/application.css`, with light surface/container and outline tokens. The screenshot's sidebar, metric order and card shapes are the visual baseline.

## Synthetic acceptance data

The isolated Compose fixture uses password `password` and invented names and medicines. Freeze the dashboard clock near a local day boundary and include two visible people, a hidden person in the same household, and another household. Give the visible people a routine item, an as-needed item, a completed item, a paused item, a not-taken record, an empty selection and low/zero stock. Expected counts must derive only from selected authorised people. Use a separate empty household or selection for honest empty-state assertions. No screenshots from real or personal records enter the PR.

The medication-take read API has pagination but no `taken_at` filter. For a mature household, the dashboard pages all authorised historical takes and retains only current-cycle rows plus the latest older take per source needed for cooldown calculations. This avoids the former 500-record failure but can require more reads as lifetime history grows; a future API date filter would reduce that cost without changing dashboard semantics. The read remains bounded by the API's authorisation and reveals only selected-person data in the page.

`task docs:build` passed with `UV_CACHE_DIR` directed to `/private/tmp` because the sandbox cannot write the default user cache.

## PR review follow-up

The first PR review identified six in-scope behaviour and cache findings: frequency-only as-needed schedules, the later of dose-cycle reset and cooldown, authorised unassigned equivalent stock for household managers, profile-local schedule dates, taper-step PRN limits and intervals, and stale public assets in the service worker. Tests reproduced each behaviour before its repair, except the taper interval test was saved after an initial implementation. For that interval case, the owner reverted only the interval-step lookup, confirmed the saved browser test failed at the old top-level deadline, then reapplied the fix and verified the expected local time. This sequence is recorded as it happened rather than claimed as an original test-first implementation.

A separate browser fixture initially assigned the stock source to the owner while the restricted member selected their own person, so no task was rendered. The fixture now gives the member their own source assignment and self grant. The member sees only the out-of-stock source and must see `Out of stock`; the owner can see an unassigned equivalent in-stock medication and must see `Available`.

Independent follow-up review found three more gaps introduced or exposed by those fixes. The 27-case focused browser suite recorded 24 passes and three genuine failures: an inactive same-person assignment did not authorise equivalent stock for a restricted member; a taper schedule with no step on the local day rendered an available PRN task; and the service worker cached a query-bearing asset URL and a redirected private response. These failures are the RED baseline for the final narrow repairs.

The final isolated focused browser run passed **27/27** cases on subnet `10.252.119.0/28`. Restricted equivalent stock now considers authorised same-person assignments even when their source is inactive, taper gaps no longer project a PRN task, and the service worker refreshes only canonical public assets with a matching response URL and media type. The worker rejects query-bearing and redirected responses from its cache, retains a patient-free offline fallback, and evicts the older public cache on activation. An independent read-only review rechecked these three repairs and found no remaining issue in those paths.

Serial per-source occurrence reads and a remembered person selection for a fresh PWA launch remain separate product/performance follow-ups. The manifest launches through authenticated household routing as required by this tranche. No clinical write route or public API schema is changed.
