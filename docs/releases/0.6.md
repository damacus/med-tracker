# MedTracker 0.6 release notes

These notes describe merged work for the forthcoming 0.6 release. They do not
announce a production deployment or acceptance of every migration milestone.

## Before installing

MedTracker now runs as a Rust application using Loco 1.2, Tera and PostgreSQL 18.
Start with a new empty database and fresh accounts. Rails passwords, passkeys,
authenticator enrolments, sessions and recovery tokens are not imported. Existing
Rails sessions cannot sign in to the Rust application. Register new credentials
and configure the intended household access in the new installation.

There is no Rails data import, populated-database adoption or reverse migration.
Keep any existing installation and its data separate; never reset it to install
this release. Rust-created records cannot be restored into Rails as a rollback.
See the [fresh Rust rollout guide](../operations/loco-cutover-runbook.md).

There is no supported rollback from 0.6 to Rails. A full Rails export at the
transition is an operator action, not an automatic import or a claim that an
export has already happened. Any retained Rails site contains only its
pre-cutover state. Preserve data written in 0.6 with a separate Rust-side export;
returning to the old site would not carry those records back. These notes do
not promise that Rails can import that export or provide a lossless switchback.

## Merged changes

- Account signup, invitations, password and passkey sign-in, optional TOTP,
  recovery and session controls use native Better Auth. Passkey-only users add
  a password before enabling TOTP. Recovery codes complete the second sign-in
  step; they do not sign in alone.
- Household administration includes member controls, invitation sending status,
  bulk access changes and security history. Sending status does not prove inbox
  delivery. Household membership alone does not define authority over a person's
  treatment plan.
- Dose and treatment forms use validated typed commands. Malformed dose retries
  retain conflict responses instead of changing them into validation errors.
  Stock deduction and clinical history remain part of the recorded operation.
- Deleting a storage location is rejected while medication or historical doses
  reference it. Empty, unreferenced locations can be deleted without cascading
  through care records. Optional medication locations remain unfinished.
- Rust-native encrypted portability supports version 3 without obsolete person
  location memberships. Older v1/v2 bundles containing those obsolete links are
  rejected. Medication storage locations and historical taken-from locations
  remain distinct. This is not a Rails importer or a profile ZIP restore feature.
- Root Loco server, worker and scheduler images support `linux/amd64` and
  `linux/arm64`. The image workflow checks native builds and can publish the
  tested images through its separate manual publication step. The existing Rails
  image publisher remains separate. See [image operations](../operations/loco-images.md).

## Still in progress

The [0.6 milestone](https://github.com/damacus/med-tracker/issues?q=is%3Aopen+milestone%3Av0.6.0) remains
open. In particular, the remaining permission changes
([#2682](https://github.com/damacus/med-tracker/issues/2682)), OAuth consent work,
and account-owned care/history and shared-plan work are not claimed complete by
these notes. Physical phone-camera acceptance is also outstanding.

Use the owner's normal image/version upgrade process when a release is
authorised. Observe startup and application behaviour during that release;
there is no separate rehearsal or runtime evidence dossier. Image publication,
site publication and production deployment are separate actions.
